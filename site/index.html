Sandboxed sessions for coding agents

The model is local.The blast radius should be too.

A local or uncensored model does what the prompt says. The agent wrapped around it starts with your whole disk and your whole network.

paddock is the fence. It runs the agent inside a sandbox the operating system enforces, and you settle the tools, the domains and the one writable directory before the first token.

§ 01

One command, one screen, then it is running

paddock run starts a sandboxed session in the terminal you are already in. There is no daemon, no multiplexer and no tab to open. It opens on the profile you launched last, so the ordinary case is L and then enter.

The confirm screen is not optional, and it does not shrink for a repeat launch. That is the whole promise of the tool: the thing granting the permissions says out loud what it granted, with the domain groups expanded into the domains they open and the paths written as they will be.

Inside herdr the same chooser opens on prefix+s and adds what a multiplexer is for: sandboxed tabs, named sessions, and a second tab attached to a session already running. Outside it, one terminal is one session and paddock run is the whole of it.

§ 02

Every grant is decided before the first token

Nothing here is a runtime prompt the agent can talk its way past. Writes and domains are settled in the kernel sandbox, and the config directory is rebuilt per session so unticked skills and MCP servers are not there to find. These are the confirm screen's own five lines.

can run

Only the binaries you tick are on the sandbox PATH, plus whatever the chosen agent cannot start without, which is named alongside it.

Soft. An absolute path still reaches any binary on the host. On srt this is convenience and the docs say so. On msb there is no host binary to reach.

can reach

A domain allowlist, by group or by name. Everything else is refused by the OS. Tick nothing and only the chosen agent's own API stays open; pick the shell agent and the sandbox is fully offline.

Hard, with one hole. On msb, DNS is all or nothing. The gateway resolver answers for every name, not only the allowed ones, and the connection is then refused. Names are a low bandwidth channel out.

can write

Denied by default. A session gets an isolated scratch directory, or the one host directory you named, which is then the only thing on this machine it can change.

No opt out. There is deliberately no allow-everything row. A sandbox with no filesystem fence is an ordinary local tab, which the Open field already offers.

can read

Your disk, minus the credential directories paddock denies by default: ~/.ssh, ~/.aws, ~/.gnupg, ~/.config/gh. On a microVM none of it has to be denied, because none of it is in there.

can see

The chosen agent's own login, and nothing else. Files it writes back to are copies, so your real config is never touched, and no agent is handed another agent's keys, your SSH keys or your cloud credentials.

Two backends enforce that policy, and they differ in kind rather than in spelling. The chooser refuses an answer the backend cannot express rather than quietly narrowing it.

srt policy sandbox

Start
Instant. Milliseconds, which is what makes a chooser on a keybinding workable.
Boundary
Seatbelt on macOS, bubblewrap on Linux, through Anthropic's sandbox-runtime.
Shares
This machine's kernel and filesystem, minus what the policy refuses.

msb microVM

Start
175ms measured from create to a usable VM. A first agent session is about 40s, because the agent is installed in the guest.
Boundary
A libkrun microVM with a kernel and a filesystem of its own. No server, no daemon, no privileged step.
Shares
Only the directory you mounted. Your disk is not in there at all.
§ 03

The agent in the VM, the model on your GPU, one port between them

On the msb backend, naming a local port writes exactly one network rule: reach this machine, on that port. Not another port on this machine, not the internet, not even DNS. No API key leaves, no prompt leaves, and the sandbox's entire network policy is a single line.

Host

Your GPU, your server
  • ollama, LM Studio,
  • llama.cpp, vLLM
  • 127.0.0.1:11434
  • never published
example.com
allow@host:tcp:11434
~/.ssh, /Users

Guest

The agent, in a microVM
  • a kernel of its own
  • /work, and nothing else
  • OPENAI_BASE_URL set
  • gone when the session ends

The mechanism is an HTTP server on a host port, so every runtime is the same shape. paddock ships no default port and has no favourite runtime: you name the port once, in an agent file or in the chooser's network field, and the guest boots knowing where the server is in every tab.

# the agent file that opens the port, once
"api_domains": ["localhost:11434"]

# what the guest boots with, in every tab
OPENAI_BASE_URL=http://host.microsandbox.internal:11434/v1
OLLAMA_HOST=http://host.microsandbox.internal:11434

Leave your server on loopback, which is where all of them start. The microVM's gateway connects onward from the host, so 127.0.0.1 is the address the request arrives at, and your server is never published to your network to make this work. If you once switched on serving to the local network, that hands the model to everyone on the Wi-Fi and paddock does not need it.

A second server, on another port of the same host, from inside the same guest:
wget: can't connect to remote host (172.16.2.213): Connection refused Measured against msb 0.6.13, alongside a real 27B model answering a prompt from inside the guest, with the host's /Users absent and example.com not resolving.

On srt the same agent file still works, but the grant is not scoped. Seatbelt's loopback rule takes no port, so it opens every service listening on this machine, and the confirm screen says so in as many words. For the narrow version, use msb.

§ 04

What it is not, yet

paddock has had no outside security review. It is a v0.2.0 beta with one author, and a tool that hands out permissions has to be honest about its own.

  • Nobody independent has tried to break it. Read the trust model before you point it at anything valuable.
  • Verified on macOS, on Apple Silicon. The Linux path runs through bubblewrap and the test suite passes on Linux in CI, but every live sandbox check written down in the docs was run on macOS.
  • Three enforcement layers, and only two are hard. The kernel sandbox and the synthesized config directory are enforced outside the agent. The generated agent config is the agent enforcing a rule on itself: useful friction, not a boundary.
  • The tool list is a soft allowlist. It shapes what the agent finds and defaults to. It does not stop a determined caller with an absolute path. Hard per-binary blocking is on the roadmap.
  • Collection is lazy. Nothing runs in the background watching for a closed tab, so a finished session is collected at the next paddock command. Until then a microVM is still up and still holding memory. paddock gc forces it.

Read the trust model. It covers what each layer does and does not stop, the known bypasses included.
